# Make My Marriage — Database Design (v1) 

Oct 5, 2026 · @Parth Khunteta 

MongoDB Atlas, one database, twenty-two collections, every wedding-owned document carrying a `weddingId` so no query crosses a wedding. 

## 1. Conventions 

Every collection follows the same rules, so a reader who learns one document learns them all. 

### Identifiers 

- Every document has an `_id` of type `ObjectId` , generated by MongoDB. 

- A reference to another document is that document's `_id` , stored under a `<name>Id` field, e.g. `weddingId` , `eventId` , `vendorId` . 

- **Public-facing tokens are separate from** **`_id` .** Guest invite tokens, gallery tokens and entry-QR tokens are random strings in their own fields, never the `ObjectId` , so an id is never guessable from a URL. 

### Field types 

|Type|Used for|
|---|---|
|`ObjectId`|Primary keys and references|
|`String`|Text, tokens, enums|
|`Number`|Money in paise (integer), counts, capacities|
|`Date`|Timestamps and calendar dates (stored UTC)|
|`Boolean`|Flags|
|`Array`|Embedded lists and tag sets|
|`Object`|Embedded sub-documents|



**Money is stored as integer paise, never a float.** ₹50,000 is `5000000` . This avoids rounding errors; the app divides by 100 for display.

### Common fields 

Every document carries: 

- `createdAt: Date` and `updatedAt: Date` , set by the app on write. 

- `weddingId: ObjectId` on every wedding-owned collection — the isolation key. The 

- four marketplace collections and `users` are the only ones without it. 

### Enums 

Closed sets are stored as lowercase strings validated by schema, e.g. `role: "admin" | "manager"` , `rsvpStatus: "pending" | "attending" | "not_attending"` . They are documented per collection below. 

### Naming 

- Collections are plural camelCase: `weddingMembers` , `bookingRequests` . 

- Fields are camelCase. 

- Dates that are calendar-only (an event date, an installment due date) are still `Date` , interpreted in IST by the app; times of day are stored on the same field. 

### Scoping rule 

No query against a wedding-owned collection runs without `weddingId` in its filter. This is enforced in the repository layer, not left to callers, and is the single most important invariant in the schema.

### Why embedded 

A guest has 3 to 8 invitations. Reading a guest, rendering their invitation page, and recording an RSVP all touch the whole set at once, so one document is one read and one write. Per-event headcounts come from an aggregation that unwinds `invitations` and groups by `eventId` — no join. 

### Consequences 

- **Per-event guest lists** are a query: `guests` where `invitations.eventId` equals the event and `invitations.rsvpStatus` equals `attending` . 

- **Uninviting** a guest from an event pulls that element from the array, dropping its RSVP. **Entry tokens** live on the invitation, so the check-in scan resolves one array element. The index on `invitations.entryToken` makes that lookup direct. 

- A guest's `token` never changes; a reset mints a new one and invalidates the old link.

## 11. Embedding vs referencing 

The rule is simple: embed what is always read with its parent and is bounded in size; reference what is queried on its own or grows without limit. 

|Data|Decision|Why|
|---|---|---|
|Wedding settings|Embedded in<br>`weddings`|Read on every page|
|Invitations|Embedded in<br>`guests`|3–8 per guest; always read and written<br>together|
|Expense splits|Embedded in<br>`expenses`|Tiny, never queried alone|
|Vendor installments|Embedded in<br>`vendors`|Few, bounded, read with the vendor|
|Seating<br>assignments|Embedded in<br>`seatingTables`|A table holds 10–12 parties|
|Listing rating<br>summary|Denormalised onto<br>`listings`|Sort the marketplace without<br>aggregating reviews|
|Events|Referenced|Queried and linked from everywhere|
|Guests|Referenced|Hundreds per wedding; filtered and<br>paginated|
|Expenses|Referenced|Many; aggregated by category, event,<br>payer|

### The one to watch 

Embedding invitations in the guest is the decision most worth restating, because it drives the guest page, the RSVP flow and every headcount. A guest document stays small — a few hundred bytes even with eight invitations — so it never approaches MongoDB's 16 MB document limit. If a wedding ever had hundreds of events, this would need revisiting, but real weddings top out around a dozen. 

### Denormalisation, kept minimal 

The only denormalised values are `listings.ratingAvg` and `ratingCount` , recomputed on each review write. Everything else is derived live by aggregation, so there is no second copy to drift. Totals, headcounts and "spent so far" are always computed, never stored.

### Notes 

- **TTL indexes** ( `expireAfterSeconds` ) let MongoDB delete expired rate-limit counters, cached Places results and old notifications automatically, with no cron job. 

- **Sparse unique** on `checkIns (eventId, guestId)` lets many walk-ins (no `guestId` ) coexist while still blocking a duplicate scan of the same guest.

## 13. Validation, transactions and integrity 

Validation runs in two layers, and the handful of multi-document operations that must be all-or-nothing run in transactions. 

### Two layers of validation 

1. **Application (Zod), authoritative.** Every write is validated by a Zod schema in the module before it reaches the driver — types, enums, ranges (e.g. `numberAttending ≤ guestsAllowed` , `rating` 1–5), and required fields. 

2. **Database (JSON Schema), a safety net.** Each collection carries a MongoDB `$jsonSchema` validator enforcing `bsonType` , required fields and enum values, so a 

write that bypasses the app is still rejected. 

### Referential integrity 

MongoDB does not enforce foreign keys, so the app holds these rules: 

|Rule|Enforced by|
|---|---|
|A<br>`weddingMember.userId`is unique|Unique index|
|A wedding always has ≥ 1 admin|Service check before demote/remove|
|Deleting an event unsets its links|Delete service, in a transaction|
|Deleting a vendor/event keeps expenses|`$unset`of the id, not cascade|
|`numberAttending ≤ guestsAllowed`|Zod + JSON Schema|

### Transactions 

Atlas replica sets support multi-document transactions, used only where a partial write would corrupt state: 

|Operation|Steps in one transaction|
|---|---|
|Mark installment paid|Set installment<br>`paid`+ insert linked<br>`expense`|
|Accept a booking|Set request<br>`accepted`+ insert<br>`vendor`linked to<br>events|
|Delete an event|Remove its invitations from guests + unset<br>`eventId`on tasks/expenses/vendors + move<br>photos to General + delete its seating tables|
|Delete a wedding|Delete all wedding-scoped documents (section 14)|
|Write a review|Insert review + recompute<br>`listings.ratingAvg`/<br>`ratingCount`|



Everything else is a single-document write, which is atomic in MongoDB on its own. 

### Concurrency 

The two places two people might collide are the email queue (solved by the atomic claim in section 10) and seating (two members seating the same party). Seating uses a guarded update that checks the table still has capacity, so the second write fails cleanly rather than overfilling a table.

### Deleting a wedding (DPDP erasure) 

When an admin deletes a wedding, it is first marked `deletedAt` and hidden immediately, then hard-deleted within 30 days: 

1. The app runs a `deleteMany({ weddingId })` across every wedding-scoped collection: events, tasks, guests, budgets, expenses, vendors, seatingTables, checkIns, albums, photos, notifications, emailQueue, weddingMembers, memberInvites. 

2. It deletes marketplace rows this wedding authored: its `bookingRequests` and `reviews` . 

3. It deletes the R2 prefix `weddings/<weddingId>/` , removing every photo object in one operation. 

4. It deletes the `weddings` document itself. 

5. `users` records are removed if the person belongs to no other wedding; a vendor account is never touched by a wedding deletion.
